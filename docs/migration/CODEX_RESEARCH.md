## Stored auth shape and identity

codex-rs/login/src/auth/storage.rs:39-65 defines AuthDotJson. Fields: optional auth_mode, OPENAI_API_KEY, tokens, last_refresh, agent_identity (JWT string or structured record), personal_access_token, bedrock_api_key, bedrock_access_keys. No flattened map preserving unknown fields exists in this struct; unknown JSON properties would be discarded when Codex deserializes/reserializes. PrimerSwitch should therefore preserve its opaque complete imported payload and not serialize through a hand-written minimal token struct; reject unsupported modes/versions for switching while retaining encrypted backups.

codex-rs/login/src/token_data.rs:10-25: tokens has id_token (serialized raw JWT string, parsed internally), access_token, refresh_token, optional account_id. last_refresh is chrono UTC timestamp. id_token metadata includes email, plan, ChatGPT user id, account/workspace id and FedRAMP flag. JWT decoding here is metadata parsing, not signature verification (129-198); email alone is not an account key. Identity should combine provider + immutable ChatGPT user identity + selected workspace/account, retaining explicit tokens.account_id and routing metadata. Never fabricate workspace/account IDs or replace id_token with a parsed JSON object.

codex-rs/protocol/src/auth.rs:8-36 has apikey/chatgpt plus chatgptAuthTokens, headers, agentIdentity, personalAccessToken, bedrockApiKey and bedrockAccessKeys. When auth_mode is absent, manager.rs:1763-1779 infers PAT, Bedrock API key/access keys, API key, then ChatGPT. Do not assume every auth.json contains normal ChatGPT OAuth or equate API keys with subscriptions.

## Storage matrix

Default cli_auth_credentials_store is file (config/src/types.rs:112-124), not auto. Explicit CODEX_HOME must already exist and is canonicalized; default is OS home/.codex (utils/home-dir/src/lib.rs:13-60). Namespace is canonicalized path or original path fallback, lossy UTF-8, SHA256, first 16 lowercase hex chars (login/src/auth/storage.rs:237-248). On Windows, reproduce actual Rust canonical path representation, including any extended-path prefix; a generic platform path normalizer is not enough.

* file: CODEX_HOME/auth.json. Codex save truncates and writes directly, Unix creation mode0600, flushes; not an atomic compare-and-swap (storage.rs:195-223).
* direct keyring: service `Codex Auth`, account `cli|<16hex>`, serialized complete AuthDotJson. Successful save removes auth.json fallback. Delete removes both direct keyring and fallback file (235-321).
* secrets keyring: CODEX_HOME/secrets/codex_auth.age holds age passphrase-encrypted JSON secrets map with entry global/CODEX_AUTH containing serialized AuthDotJson; key is in OS keyring service `codex`, account `secrets|<16hex>`. **The same key is shared with managed-secrets local.age and MCP mcp_oauth.age. Never delete/rotate/copy this key as an account switch.** Gateway OAuth has independent suffix/key. Source secrets/src/local.rs:40-64,123-176,189-278; secrets/src/lib.rs:66-69,182-202. Missing passphrase load can create a new key in upstream load_or_create_passphrase, so a compatibility preflight must fail safely for key loss before invoking that path on existing ciphertext.
* feature secret_auth_storage selects secrets backend. It defaults ON Windows, OFF Linux/macOS, and can be changed by feature configuration/managed requirements (features/src/lib.rs:984-988, core/src/config/auth_keyring.rs:13-17,85-116). Thus Windows keyring/auto normally uses encrypted auth file + OS key, Linux/macOS normally direct JSON OS item. Either backend can occur on any OS. This is independent of file/keyring/auto/ephemeral store mode.
* auto: keyring-first load; file fallback on absent item OR any keyring load error. Save attempts keyring, falls back file on failure; keyring success removes file (storage.rs:431-456). A fallback save may leave a stale keyring entry that later masks the newer file. Switch preflight must detect dual-store disagreement and fail rather than infer newest from mtime.
* ephemeral: process-global mutex map keyed by the same path hash, never persisted. External tokens are checked before persistent storage even when configured file/keyring/auto. A separately launched process cannot adopt another process's ephemeral auth (storage.rs:459-499, manager.rs:1507-1533).

Locked dependency keyring3.6.3 is public source under artifacts. Windows Entry::new uses Generic Credential target `<account>.<service>` (windows.rs:1-22). macOS service/account generic password in User/login keychain (macos.rs:1-29). Linux Codex enables linux-native-async-persistent: **kernel keyutils cache + Secret Service**, reads cache first and only falls back to Secret Service on error (keyutils_persistent.rs:83-99). Kernel description `keyring-rs:<account>@<service>` (keyutils.rs:265-275); Secret Service attributes target=default, service, username; creation also application=rust-keyring-client (secret_service.rs:5-38). Raw D-Bus mutation alone can leave Codex reading stale kernel credentials. Must use compatible complete backend behavior, or initially decline Linux keyring/auto writes until isolated fixtures prove both stores. PrimerSwitch's own secure vault master-key namespace is unrelated.

## APIs, ownership and switch safety

Use managed app-server account/login/start type chatgpt or chatgptDeviceCode, completion/cancel and account/read. OAuth persistence/refresh should stay owned by Codex. Transport/schema should be generated/negotiated for the selected executable, Rust-controlled private stdio, never UI raw tokens. Official docs recommend future Sign in with ChatGPT migration and restrict local app-server auth to local/open-source use; commercial/hosted products need the recommended auth route.

**Do not use experimental chatgptAuthTokens for PrimerSwitch now:** pinned protocol v2/account.rs:86-88 explicitly marks it internal-only/do-not-use, although current docs describe experimental external ownership. External tokens have no refresh token in the generated ephemeral payload; host must answer a refresh request within10s (app-server/src/external_auth.rs:18-75). This is neither export of managed refresh credentials nor a stable saved-account adoption API.

Stable request registry common.rs has login/read/logout but no named stored-account selection or general reload-auth endpoint. AccountSessionsAdd/List/Switch types exist in v2/account.rs:194-259, but only occur in those definitions: no registered requests/processor implementation in this pinned tag. Their presence is not callable support.

AuthManager loads/caches auth and external file changes are not automatically observed (manager.rs:2034-2041); guarded refresh reload accepts only same account (2487-2519,2844-2880). Changing shared cache does not safely retarget already-running CLI/TUI/desktop/app-server processes. Restart newly selected clients and verify account/workspace; do not claim all live clients switch.

**Cross-account write race:** refresh semaphore is process-local (manager.rs:2056); after an HTTP refresh, persist_tokens loads whatever payload is currently in the backend, merges returned fields, updates last_refresh and saves, without comparing account before save (1598-1620,3092-3106). Switching while an old process refresh is in flight can contaminate the new account cache. A PrimerSwitch lock cannot stop unaware Codex processes. Production shared-cache switching must require quiescent relevant writers and abort on external mutation; an independent PrimerSwitch OAuth refresher makes this worse. Rotated credentials from Codex must be atomically adopted into encrypted per-account snapshots after verifying source binding/owner/generation, with conditional recovery and no stale rollback.

account/read refreshToken:false directly uses auth_cached, not proactive auth() (account_processor/workspace_routing.rs:157-238); correction to an earlier message. It can load effective config and perform workspace routing discovery. Deprecated getAuthStatus with default flags and quota endpoints can call auth(), which may proactively refresh expiring tokens (manager.rs:2390-2406,3004-3025). A separate sidecar should not inspect user auth in a supposedly read-only discovery stage unless explicitly authorized as an auth owner.

Concrete first switch contract: identify pinned executable + canonical target home + effective backend + policy + expected active identity; capture opaque old/new encrypted snapshots; ensure no relevant uncontrolled writers; recheck active generation; journal before scoped mutation; write only auth payload in its correct backend; verify newly launched Codex account/workspace; adopt post-refresh rotation; finish journal. On uncertain external writes, refuse/reconcile rather than rollback over newer credentials. No logout-first, no whole CODEX_HOME replacement, no plaintext forced fallback, no profile rewriting. File-mode initial adapter is substantially narrower; keyring/auto requires additional perOS backend fixtures. Ephemeral and restricted/unknown auth modes initially unsupported for shared-cache switching.

## Explicit guards

Effective config is layered: packaged/system/MDM/enterprise/user/profile/project/session/legacy managed. Preserve all layers. config/read(includeLayers:true,cwd) + configRequirements/read can expose resolved config/origins and managed login/store/baseURL/provider restrictions; validate selected executable schema before use. Config APIs are not a license to read/log raw auth-looking config values. Auth bootstrap has to honor cli_auth_credentials_store, chatgpt_base_url, forced_login_method, forced_chatgpt_workspace_id, allowed_login_methods and allowed_chatgpt_workspaces intersection; managed feature requirements can also constrain backend. Sources core/src/config/auth_keyring.rs:34-77; config/src/auth_policy.rs:10-58; config/src/config_requirements.rs:164-167; app-server-protocol/src/protocol/v2/config.rs:389-422. Public requirements schema lacks an explicit workspace allowlist field, so do not infer unrestricted from it alone.

Environment presence guards, without logging values: CODEX_HOME, CODEX_API_KEY (takes precedence when enabled, e.g.exec), CODEX_ACCESS_TOKEN (PAT/agent identity), OPENAI_API_KEY (detected/login or provider-specific; not automatically equivalent to CODEX_API_KEY), OPENAI_FEDERATION_RULE_ID, OPENAI_IDENTITY_TOKEN_FILE, OPENAI_WORKLOAD_IDENTITY_CONTEXT (external workload identity), CODEX_APP_SERVER_LOGIN_CLIENT_ID, CODEX_REFRESH_TOKEN_URL_OVERRIDE, CODEX_REVOKE_TOKEN_URL_OVERRIDE. Never launch a user token-file reader/provider auth command during discovery. Source login/src/auth/manager.rs:214-216,953-976,1499-1538; workload_identity.rs:133-158,256-258; protocol/shell_environment.rs:9-11.

Provider guards: model_provider/model_providers, requires_openai_auth, base_url/model_catalog_url, env_key, experimental_bearer_token, command-backed auth, AWS, gateway_oauth, http_headers/env_http_headers, auth routing, residency/FedRAMP. Account change must not silently change billing/custom endpoints, execute auth commands, bypass workspace/login requirements, or send subscription credentials to user/custom URLs (model-provider-info/src/lib.rs:133-190). Legacy enforced restriction violations can actively logout existing credentials (manager.rs:1325-1454), so do not start an incompatible candidate on the real target home to test it.

Quota: prefer account/rateLimits/read; keep every limitId/window/reset/plan/credits as provider-native nullable state. Pinned response includes ordinaryUsageAllowed and accountId; null permission cannot be inferred from percentage/reset. Poll supportsLunaReserve:false and excludeResetCreditDetails:true initially to avoid experimental exposure/detail calls. Never auto-consume reset credits or send emails. API-key/Bedrock/custom providers do not share ChatGPT quota. Verify quota response owner before displaying/scheduling switches (protocol/v2/account.rs:315-344).

## Recommended implementation gates

1. Ship provider boundary, Codex executable/schema/version discovery and fake stdio protocol tests first, no auth reads during discovery.
2. Explicit authorized import/encrypted snapshot for supported managed ChatGPT payloads, preserved unknown fields and separate API-key type. Offline fixtures for all known auth modes and missing fields; identity/workspace mismatch must fail.
3. Isolated temporary home/keyring tests for file, direct keyring, secrets keyring, auto disagreement/locked/unavailable/lost key and ephemeral. Match exact pinned namespace and Linux cache behavior. No ordinary tests touching real home/keyring.
4. Prove new managed login does not overwrite existing active credentials by using separately owned stable home/context; adopt tokens only after successful verified login. Cancel/failure retains prior account.
5. Add manual switching only after restart/quiescence, external-writer CAS/journal recovery and refresh-rotation adoption fixtures. Running-client claim remains new-process selection until official reload/selection API exists.
6. Quota integration follows verified ownership; Codex-specific auto-switch policy is a separate final gate, not reuse of Claude reset policy.

Remaining limits: source research establishes behavior, not compatibility execution against native installed Codex or actual provider. No real auth/keyring/provider fixture was run. Unknown future release/schema/backends must fail closed for writes. Resolve documented/internal-only external-token discrepancy upstream before any external-token feature.
