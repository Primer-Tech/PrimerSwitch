# Implementation and evidence ledger

Updated 2026-10-22 (0.2.6 manual Claude identity recovery). The owner authorized implementation, a public repository and parallel GPT-6.1 Sol agents. English is the default language and Romanian is supported. The owner approved Direction A, the dark dashboard generated by the image model; the later Primer branding request is recorded in [BRANDING.md](../design/BRANDING.md); [the design record](../design/PROPOSALS.md) preserves proposals and implemented screenshots.

## Unreleased: Codex API-key accounts

The owner asked to add an OpenAI API key in the app and to switch to it by hand, and back to a ChatGPT account, through the existing switch flow. No version bump or release is part of this change; an unsigned local installer was built and installed over 0.2.6 (see Local installation below).

Real Codex 0.163.0-alpha.2 evidence from owner-authorized probes (isolated homes, no PrimerSwitch involved): `codex login --with-api-key` writes `auth.json` as exactly `auth_mode` `apikey` plus `OPENAI_API_KEY`, with no tokens, and a real request with such a file works. PrimerSwitch writes the same shape. A key from an older import keeps its stored shape, which has no `auth_mode`; Codex infers API-key mode from it per the research notes, but that shape was not tested live.

Scope. A new **Add API key…** dialog sends the key to a native command (`codex_add_api_key`) that wraps it in a zeroizing string, validates it (trimmed, `sk-` prefix, printable ASCII, 20 to 512 bytes), stores it in the encrypted vault under a trimmed 1 to 60 character name and never selects it. Snapshots carry only the last four characters; no key, response body or error text that could echo input crosses the boundary, and failures use one generic stable reason. The key field is a password input that is emptied at submit, in `finally` and on cancel, escape or close. Manual switching writes the key through the same atomic path as a ChatGPT login, keeps the outgoing login first and restarts the Codex daemon; the platform `auth.json` validation now accepts the API-key shape and still refuses mixed key-and-token, agent-identity, personal-access-token and Bedrock payloads. An external `codex login --with-api-key` is adopted like any unknown login, and a key already saved (compared by value, not by formatting) is never duplicated.

Late ChatGPT refresh. An older Codex process (before 0.163) that finishes a ChatGPT refresh after the key was written merges the rotated tokens into the key file and keeps the key and the mode, giving a file with both. PrimerSwitch recognises exactly that shape (a non-empty key, mode `apikey` or absent, a valid ChatGPT login in `tokens`, and no agent identity, personal access token or Bedrock field), splits it into a normal key payload and a normal ChatGPT payload, moves the rotated tokens into the saved account of the same owner (or keeps them as a new account), adopts the key without a duplicate and selects the key account, because Codex stays in key mode. This runs in the observer, in the outgoing-login step of every switch, at the end of a switch and in "Import current Codex login". Before, such a file was unsupported: the tokens were lost and every switch back to ChatGPT failed. The file is not rewritten by this repair; the next switch replaces it. Any other mixed file is still unsupported, is never written over, and is still refused as a write target.

A switch whose file changes during the daemon drain into something that is neither the target, a hybrid, a splittable file nor an adoptable login (an agent identity, no login, an unreadable file) no longer reports success: the switch ends with an external-change failure, the "switching" state is cleared and no login is selected.

Lampese import of a key now trims it and matches existing key rows by value like every other adoption path, so a saved legacy key (no `auth_mode`), an externally observed key or a key added by name is not renamed, reset (sign-in state, failures) or counted as imported again; blank keys are skipped.

Safety limits. Automatic switching, preferred returns, quota-driven selection and the last-line eligibility guard only ever consider saved ChatGPT accounts (the automatic fallback described below adds the one exception, a fallback plan that the guard checks separately), and an API key is never a source of headroom. A key is never read for quota: per-account and bulk refresh and the post-switch reading return without error or sign-in state. The key row has no usage windows; the UI shows "Billed per token · no ChatGPT plan limits". Use is billed per token to the OpenAI API account, outside any ChatGPT plan. There is no automatic fallback to an API key (a possible later phase).

Flex processing for an API key (unreleased, after the local installation above). The owner asked to cut cost while an API key is active. Verified facts, from tests on 2026-10-29 with Codex 0.163.0-alpha.2 and the v0.163.0 sources, in isolated homes: `service_tier` in `config.toml` is a free string. Codex sends `"service_tier":"flex"` in the Responses request when the value is "flex" and omits it for "default" or when it is unset. The terminal UI honours a configured "flex" unconditionally, although the model list under an API-key login only offers `priority` and `ultrafast`, so there is no `/flex` toggle. An API key with Flex works, slower, and sometimes fails with "Selected model is at capacity", which Codex does not retry. A ChatGPT login with Flex fails with `400 Unsupported service_tier: flex`. A thread keeps its tier in its saved state, and a new terminal reads its tier from its own config at launch, so a config change reaches only sessions started after it. The owner's config has a top-level `service_tier = "default"` and `fast_default_opt_out = true`.

Scope. Each saved API key has a setting **Use Flex processing**, off by default, kept in the encrypted state (records saved before it load unchanged). The toggle is in the key's details, with the text "Cheaper, but slower, and a request can fail when Flex capacity is full; Codex does not retry that error. Only for this API key. Sessions that are already open keep their current tier." The row of a Flex key shows "Flex". The option needs a qualified Codex home and Codex 0.163.0 or newer (a pre-release of 0.163.0 counts); otherwise the capability is blocked with a reason, and switching to a Flex key is blocked too, so it is never used at the standard tier by mistake. Turning the option off is always possible. The toggle calls one native command, `codex_set_api_key_flex({id, enabled})`, which returns the Codex snapshot. Automation is unchanged: keys are still never automatic targets.

What is written. PrimerSwitch manages one value: the top-level `service_tier` of `$CODEX_HOME/config.toml`. It sets it to "flex" only while a Flex key is the active login, and puts back what was there (the old value, or no key, or no file) when the active login is anything else. A `service_tier` inside a table or profile is never touched, and no other file is written. The saved mark is `flex_applied` in the Codex state: the previous value as TOML text, and whether the file existed. The mark is saved before the file changes, so a crash can never leave Flex in `config.toml` without it.

Edit mechanism. The file is edited as bytes. `toml_edit` 0.25.15 (already in the lock file through `proc-macro-crate`, `parse` feature only, no new download) parses the file only to find the value and the key line by source span; a text splice replaces just that span, or adds `service_tier = "flex"` as the first line when the key is absent (after a byte order mark, with the file's own line ending). The edited text is parsed again and must still say what it should. Comments, CRLF or LF, spacing, tables and every other key stay byte for byte; a literal string comes back as a literal string. A file that does not parse, is not UTF-8, or has a `service_tier` that is not a plain string is refused and left untouched. The mark comes from a separate step, `plan`, that reads the file and writes nothing; it also refuses a value that a restore could not put back (a multi-line or triple-quoted string, or one longer than 256 bytes). The edit itself only sets "flex" and does nothing when the file already says so, so a retry after a conflict cannot change the saved original value; it refuses the same values. The write is atomic (a staged file in the same directory, then replace) under the context lock, and it is refused when the file changed since it was read; it is retried up to four times when Codex rewrites the file meanwhile. On Unix the new file keeps the old mode; on Windows it inherits the directory's access rules, as a file created by Codex does. A file that PrimerSwitch created is removed again when it is empty. If the owner already had `service_tier = "flex"`, nothing is written and the setting is never removed. If the owner changed the value while Flex was on, the new value is left and only the mark is cleared.

Order of a switch. To a Flex key: plan the mark and save it, then set Flex, then write `auth.json` and restart the daemon; if the mark cannot be saved the file is not touched; if the config cannot be written the switch stops with `flexConfigFailed` and the login is unchanged (a Flex key is never switched to at the standard tier by mistake), and the mark is taken back unless the file may already say Flex, in which case the next restore puts the value back; if the login write fails afterwards, the config is put back. Away from a Flex key (to ChatGPT or to a key without Flex): restore the value before the new login is written; a failed restore never blocks the switch, the mark stays, `flexRestoreFailed` is shown as a warning and the restore is retried on every background tick. Switching between two Flex keys keeps Flex and the first mark. The notices are "Flex is on. New Codex sessions use Flex; sessions that are already open keep their tier." and "Flex is off again. A session started while Flex was on can fail on ChatGPT with 'Unsupported service_tier: flex'; start a new session." (English and Romanian).

Reconcile. At startup, after every observed change of the active login (also one made outside the app, for example `codex login`), after a toggle and on every tick: if a mark is set and the active login is not a Flex key, the value is restored; if the active login is a Flex key and no mark is set, Flex is applied. A failure to apply is shown as a warning (`flexConfigFailed`), never silent. Both crash windows are safe: a mark saved with a file that does not say Flex is cleared by the next restore, which leaves the file byte for byte; a mark with Flex in the file is restored unless a Flex key is active. The toggle first reads the live login, so a login changed outside the app within one tick is honoured: Flex is never applied under ChatGPT. PrimerSwitch's own write is a normal config change: the Codex context is qualified again after it and stays valid. A config that makes the context restricted (a default profile, a forced login method, a custom provider) blocks the option through the existing qualification. A restart test found that the step that sanitizes saved state at load dropped the mark; it now keeps it.

Automatic fallback to an API key (unreleased, after the Flex work). The owner asked that PrimerSwitch move Codex to an API key by itself when every ChatGPT account is at its limit, and back when one recovers. This starts billing per token without a click, so every gate fails closed and the guarded switch asks every condition again just before it writes the login.

Scope. Each saved API key has a setting **Use as fallback**, off by default, kept in the encrypted state (`fallback`, records saved before it load unchanged) and set with the native command `codex_set_api_key_fallback(id, enabled)`; it is refused for a ChatGPT account and while a sign-in or switch runs. It only acts while automatic switching is on; the key's details show a hint when it is off, and the setting can still be saved. Turning it on in the window opens a confirmation first (billing consent): "Codex bills this key per token, outside your ChatGPT plan. PrimerSwitch will switch to it by itself when every ChatGPT account is at its limit and switch back when one recovers. Set a monthly budget on the OpenAI project." Nothing is saved on cancel. Turning it off needs no confirmation. The confirmation is a window rule only: the native command itself does not ask, like every other setting. With Flex on the same key it works through the existing switch path (the Flex config is written before the login and a Flex failure aborts the automatic switch); the details and the confirmation warn that a Codex session started while the key is active with Flex fails on ChatGPT after the automatic return until a new one is started.

Engage (ChatGPT to key), in the exhaustion branch of `CodexEngine::automation`, new plan variant `CodexAutomation::Fallback` and plan kinds `Switch`, `Return`, `KeyFallback`, `KeyReturn` (they replace the old `returning` flag, so the guard cannot confuse a natural return with a key return). All must hold: automatic switching on; not cooling down; no switch or sign-in running and no blocked setup; the active login is a saved ChatGPT account with a fresh reading (at most 15 minutes old) at its threshold or at a limit; `next_candidate` is none and every other enabled ChatGPT account is known unusable (read, no error, no sign-in needed, at its threshold); and a key has the setting on, is included in automatic switching, is not in `account_errors` and passes the switch capability (the Flex version gate included). With several keys, the lowest priority number wins, then the lowest id. Beyond the brief: a "limited" reading whose reset time has already passed proves nothing, so such an account is read again first (`Refresh`, bounded by the existing recovery retry floor, or a wait right after an attempt) and nothing is engaged until the new reading proves it. When no key qualifies the existing all-limited notice is unchanged.

Marker. `fallback_engaged {key_id, from_account_id, since}` is kept in the encrypted state (kept by `sanitize` only while its key is saved). It is set right after the login write of a fallback plan (and saved best effort; `finish_switch` saves again), so a crash cannot lose it. It is cleared whenever the active login is not that key (the return, a manual switch, a login made outside the app, a deleted key), and never before the first observation of the login, so a start without a readable login keeps it. The snapshot carries `fallbackEngaged {keyId, since}` only while that key is the active login, the setting is on and the app is not in demo.

Return (key to ChatGPT). Active login is a key with the setting on, automatic switching is on, the app is not cooling down, the manual hold has passed, and a ChatGPT account has a fresh reading with headroom (`next_candidate`, the same ranking as ordinary switching). If the best candidate's reading is stale it is read first (`Refresh`, bounded as before). While a key is active the existing scheduling already reads the ChatGPT accounts: an account whose window has reopened is read within the recovery retry floor (2 minutes) and the others hourly; a test pins this. After a return the marker is gone and nothing engages again before the cooldown. A manual switch to a fallback key is held 15 minutes, then follows the same return rule (turn the setting off to stay on the key).

Guards. The last-line check (`automatic_target_still_eligible`) now matches on the plan kind: ordinary Switch and Return plans still need a saved ChatGPT account as active login and target (an API key is refused as target); a KeyFallback plan needs a ChatGPT active login, a key target with the setting on and `key_fallback` yielding `Engage` for that same key, so a stale reading, a new candidate, an unread, failed, signed-out or reopened account, automatic switching turned off, the key excluded, switched off or blocked, or a better key all abort with the external-change failure and change nothing; a KeyReturn plan needs the key as active login with the setting on and `automatic_return` giving the same target. The check runs after the observation inside `begin_switch_guarded` and again inside the transaction loop. The expected owner became an `ExpectedLogin` (ChatGPT binding, or an API key compared with `same_api_key`), so a different key or login written meanwhile stops the switch. A failed automatic fallback (Flex failure, daemon restart failure, external change) notifies once (`failure_notice_due`) and is not retried within the cooldown, because the cooldown starts before the attempt.

Notices and window (English and Romanian). A notification on engage ("Every ChatGPT account is at its limit. Switched to API key X. Codex now bills per token. PrimerSwitch returns by itself when an account recovers.") and on return ("Account Y has usage again. Switched back from API key X."). A banner on the Codex page, without a dismiss button, while the key is active with the setting on: "Using API key X (billed per token) since HH:MM because every ChatGPT account is at its limit. PrimerSwitch returns automatically when one recovers.", with **Switch back now** when a ChatGPT account can be switched to. The key's row carries a "Fallback" tag; the key dialog's text no longer says automatic switching never uses a key. No key, response body or error text appears in any snapshot, notice or window.

Limitations. There is no spend cap: OpenAI offers no usage reading for a key, so PrimerSwitch cannot stop or even see the billing; the monthly budget on the OpenAI project is the only cap, and the confirmation says so. The return needs only a ChatGPT account below its threshold (the same ranking as ordinary switching), not extra headroom, so an account that is just below its threshold can fall back to the key again after the cooldown; this is intended to be cheap rather than sticky, and the owner can turn the setting off. A session started while the key is active with Flex fails on ChatGPT after the return (the same limit as the Flex setting, now warned about). Between the proof and the write the last-line check asks again, but it cannot see a limit that is reached while the key is being written. If the daemon restart fails after the login was written, the key is already the login: the marker is set and the usual warning is shown. Not verified: a live automatic fallback with real accounts, a live return, and the native window (jsdom tests only). No version bump, release, push or installer is part of this change.

Review pass 1 (automatic fallback). One adversarial pass found five confirmed medium findings, no high and no low; all five are fixed. The review budget for this change was one pass, so the only proof of the fixes is the new tests and the mutation checks below; the fix delta was not reviewed by a second model. (1) The reset check skipped the active account: its own reading can be fresh while its window has reopened, so a key could be billed although the account had recovered. `key_fallback` (and so the write guard) now applies the reset-passed gate to the active account too: it is read again when due (`Refresh`), otherwise `Wait`. (2) Another account's "limited" reading was trusted from its stored percentage only, so after a restart (the in-memory error map is empty and nothing is verified yet) a failed read or an old reading could not stop the key.
